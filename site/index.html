It doesn't chat

      
It's a router, not a chatbot. It emits machine-readable decisions your agent, helpdesk, or dispatcher can act on directly.

    

    

      
It doesn't guess

      
Out-of-scope requests hit the calibrated escalate route. Small models shouldn't pretend to know things — this one doesn't.

    

    

      
It doesn't argue

      
No temperature, no sampling, no prompt drift. Deterministic softmax over your routes — the same request gets the same answer, every time.

Mixture of experts — one trunk, many brains.

  

    The frozen 7M trunk is the shared brain. Domain knowledge lives in
    ~7KB heads you can ship, swap, and audit like config files.
    A gate head picks the expert; the expert picks the route.
  

  

    Each head declares its own feature tap — last-token, mean@-3,
    max@-3 — so a single instance serves the pooling recipe that actually
    won each domain's eval. Known-domain clients can also pin their expert and skip
    the gate entirely.
  

  

    
                 ┌─────────────────────────────────────┐
  request  ──▶  │  mtlm-router trunk — frozen 7M model  │
  tokens         └──────────────┬──────────────────────┘
                    prefill hidden state (1 × d_model)
            ┌────────────┐ ┌─────────────┐
            │ gate.head  │ │ expert.head │   ← per-domain, ~7KB
            │ pick a domain │ │ pick a route   │
            └────┬───────┘ └─────┬───────┘
       it_helpdesk ───┘        reset_password ───┘  + calibrated conf

  

  

    

      
Ship brains, not models

      
A customer deployment = the frozen trunk + a handful of kilobyte head files. Onboard a new domain by training a head on ~50 labeled examples per route — a working lane in hours; your full export is what scales it.

    

    

      
Per-head pooling

      
Pooling wins aren't uniform — mean@-3 takes the synthetic experts, max@-3 takes long-prose traffic, last-token keeps the gate. mhd2 flags carry each recipe; the server just obeys.

It trains on its own traffic.

  

    Every /v1/route decision is logged. A daily flywheel harvests
    the log, files uncertain rows into a persistent review queue, merges judged verdicts into
    the train-only corpus, and dedupes before retraining. The gate thickens from
    real requests — never from its own confident predictions.
  

  

    
decisions.jsonl ──▶ harvest ──▶ review queue ──▶ judge ──▶ train corpus ──▶ new head
                 (replay domain-less rows · seen = resolved only · dedupe at merge)

Honest limits.

  

    

      
It's a router, not a reasoner

      
It can't summarize, explain, or compose. If you need text generation, route to a bigger model — that's exactly what escalate is for.

    

    

      
Thin lanes exist

      
Free paraphrase abstains — the municipal head delegates novel phrasing even when close. That's the design: thicken a lane with client-labeled rows via the flywheel, don't lower the bar. The manifest ships per-domain row counts so you see weak lanes first.

    

    

      
Calibration ages

      
Temperature was fit on today's request mix. Traffic drifts; refit from labeled production rows before trusting the confidences downstream.

    

    

      
Verify before authority

      
Run it as a shadow router first. Promote to authoritative only after real traffic proves the gate + head on your request mix.

One tarball. Runs anywhere.

  

    The whole stack — server binary, tokenizer, int8 model, heads — ships in one
    fully self-contained ~7.8MB tarball.
    Untar, run ./start.sh, done. No anvil install, no pip, no model
    download, no license server — nothing leaves the machine.
  

  

    
$ tar xzf mtlm-router-v0.3.0-linux-amd64.tar.gz && cd mtlm-router-v0.3.0-linux-amd64
$ ./start.sh &
$ curl localhost:8097/v1/route -d '{"state":"Dépôt illicite. micro onde","expert":"mairie"}'
{"route":"depot_illicite","domain":"mairie","action":"tool_call","confidence":0.999,...}

  






  
Agent-operable, not just agent-readable.

  

    The tarball ships a mtlm-router CLI built for AI agents:
    JSON-only stdout, semantic exit codes, an embedded guide, a
    health-polled daemon lifecycle, and content-hash self-update. The server self-describes —
    /guide, /llms.txt, /v1/whoami, /v1/feedback.
    28/28 on cli-spec-conformance — checked, not claimed.
  

  

    
$ ./mtlm-router daemon start        # loopback, polls /_health — never a fixed sleep
{"daemon":"up","port":8097,"url":"http://127.0.0.1:8097"}
$ ./mtlm-router guide               # embedded operator manual (JSON)
$ ./mtlm-router update --check      # content-hash self-update → .bak rollback
$ ./mtlm-router daemon stop         # clean POST /_shutdown
