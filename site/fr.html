Il ne discute pas

      
C'est un routeur, pas un chatbot. Il émet des décisions lisibles par machine que votre agent, helpdesk ou répartiteur peut exécuter directement.

    

    

      
Il ne devine pas

      
Les requêtes hors périmètre tombent sur la route calibrée escalate. Un petit modèle ne devrait pas faire semblant de savoir — celui-ci ne le fait pas.

    

    

      
Il ne débat pas

      
Pas de température, pas d'échantillonnage, pas de dérive de prompt. Un softmax déterministe sur vos routes — même requête, même réponse, à chaque fois.

    

  






  
Pensé pour les workflows de PME, pas pour les datacenters.

  

    Les requêtes qui mangent le temps d'une PME sont des décisions, pas des
    dissertations — trier la boîte mail, dispatcher le ticket, router le devis.
    C'est exactement le travail d'un routeur.
  

  

    

      
Tri emails & tickets

      
Devis, commandes, litiges, demandes urgentes — classés, priorisés et poussés vers la bonne file ou l'ERP. Plus de copier-coller, plus d'emails perdus.

    

    

      
Commandes ops typées

      
« Redémarre le spouleur sur srv2 », « marque la commande 4412 pour revue » — le langage naturel devient une action typée que votre automatisation exécute, ou un escalate quand il ne faut pas.

    

    

      
Relais conformité

      
Confiance faible ou requête risquée : escalade vers un humain plutôt qu'exécution. Piste d'audit incluse — chaque décision est journalisée avec sa confiance.

    

    

      
Une instance, plusieurs clients

      
Intégrateurs : déployez le même tronc chez chaque client et livrez une tête par client — un fichier ~7 Ko entraîné sur son vocabulaire en quelques heures, pas un modèle sur mesure.

    

    

      
Porte d'entrée pour la grosse IA

      
Placez-le en shadow devant votre LLM hébergé pour mesurer ce qu'il aurait pu traiter localement — puis ne coupez la facture API que là où les données le disent.

    

    

      
Pas besoin d'équipe ML

      
Une archive, un binaire, un endpoint. Si votre stack sait faire un POST JSON, elle sait router. RGPD natif : rien ne quitte jamais votre réseau.

    

  






  
Mixture of experts — un tronc, plusieurs cerveaux.

  

    Le tronc 7M figé est le cerveau partagé. La connaissance métier vit dans des
    têtes de ~7 Ko que vous livrez, échangez et auditez
    comme des fichiers de config. Une tête gate choisit l'expert ; l'expert choisit la route.
  

  

    Chaque tête déclare son propre prélèvement de features — last-token, mean@-3,
    max@-3 — pour qu'une seule instance serve la recette de pooling qui a
    réellement gagné l'éval de chaque domaine. Les clients qui connaissent leur domaine peuvent
    aussi épingler leur expert et sauter le gate entièrement.
  

  

    
                 ┌─────────────────────────────────────┐
  request  ──▶  │  tronc mtlm-router — modèle 7M figé  │
  tokens         └──────────────┬──────────────────────┘
                    hidden state du prefill (1 × d_model)
            ┌────────────┐ ┌─────────────┐
            │ gate.head  │ │ expert.head │   ← par domaine, ~7 Ko
            │ choisit le domaine │ │ choisit la route │
            └────┬───────┘ └─────┬───────┘
       it_helpdesk ───┘        reset_password ───┘  + confiance calibrée

  

  

    

      
Livrez des cerveaux, pas des modèles

      
Un déploiement client = le tronc figé + quelques fichiers de têtes de quelques Ko. Onboardez un nouveau domaine en entraînant une tête sur ~1 000 lignes labellisées — des heures, pas des semaines.

    

    

      
Pooling par tête

      
Les gains de pooling ne sont pas uniformes — mean@-3 gagne sur les experts synthétiques courts, max@-3 sur le trafic en prose longue, last-token garde le gate. Les flags mhd2 portent chaque recette ; le serveur obéit.

Il s'entraîne sur son propre trafic.

  

    Chaque décision /v1/route est journalisée. Un flywheel
    quotidien moissonne le log, range les lignes incertaines dans une file de revue
    persistante, fusionne les verdicts jugés dans le corpus d'entraînement et déduplique
    avant ré-entraînement. Le gate s'étoffe sur des requêtes
    réelles — jamais sur ses propres prédictions confiantes.
  

  

    
decisions.jsonl ──▶ harvest ──▶ file de revue ──▶ verdict ──▶ corpus train ──▶ nouvelle tête
                 (replay des lignes sans domaine · seen = résolu seulement · dédup à la fusion)

  






  
Regardez une vraie lane décider.

  

    La lane mairie fait tourner la tête phare — entraînée sur un export de production
    réel, servie en direct sur la démo publique (pin expert:"mairie") :
    dépôt illicite. micro onde → depot_illicite @ 1.00,
    demande de passeport → escalate → delegate.
    ~190ms par décision sur CPU.

Limites honnêtes.

  

    

      
C'est un routeur, pas un raisonneur

      
Il ne résume pas, n'explique pas, ne compose pas. Besoin de génération de texte ? Routez vers un plus gros modèle — c'est exactement le rôle de escalate.

    

    

      
Des lanes fines existent

      
La paraphrase libre s'abstient — la tête mairie délègue une formulation nouvelle même proche. C'est voulu : étoffer une lane avec des lignes client labellisées via le flywheel, pas baisser la barre. Le manifeste livre les comptes par domaine pour voir les lanes faibles en premier.

    

    

      
La calibration vieillit

      
La température a été ajustée sur le mix de requêtes du jour. Le trafic dérive ; réajustez depuis les lignes de production labellisées avant de faire confiance aux confidences en aval.

    

    

      
Vérifiez avant d'autoriser

      
Lancez-le d'abord en routeur shadow. Ne le promouvez en autoritatif qu'après que le trafic réel a prouvé le gate + la tête sur votre mix de requêtes.

Une archive. Tourne partout.

  

    Toute la stack — binaire serveur, tokenizer, modèle int8, têtes — tient dans
    une archive autonome de ~7,8 Mo.
    On extrait, on lance ./start.sh, c'est tout. Pas d'install d'anvil,
    pas de pip, pas de téléchargement de modèle, pas de serveur de licence —
    rien ne quitte la machine.
  

  

    
$ tar xzf mtlm-router-v0.2.0-linux-amd64.tar.gz && cd mtlm-router-v0.2.0-linux-amd64
$ ./start.sh &
$ curl localhost:8097/v1/route -d '{"state":"Dépôt illicite. micro onde","expert":"mairie"}'
{"route":"depot_illicite","domain":"mairie","action":"tool_call","confidence":0.999,...}

  






  
Pilotable par agent, pas juste lisible.

  

    L'archive embarque une CLI mtlm-router pensée pour les agents IA :
    JSON seul sur stdout, codes de sortie sémantiques, guide embarqué,
    cycle de vie du démon sondé via /_health, et self-update par hash de contenu. Le serveur se décrit lui-même —
    /guide, /llms.txt, /v1/whoami, /v1/feedback.
    28/28 sur cli-spec-conformance — vérifié, pas juste affiché.
  

  

    
$ ./mtlm-router daemon start        # loopback, sonde /_health — jamais de sleep fixe
{"daemon":"up","port":8097,"url":"http://127.0.0.1:8097"}
$ ./mtlm-router guide               # manuel opérateur embarqué (JSON)
$ ./mtlm-router update --check      # self-update par hash → retour .bak
$ ./mtlm-router daemon stop         # POST /_shutdown propre
